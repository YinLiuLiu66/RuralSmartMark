## ✅ 已定

### #1 · 数据库选型
**结论**：PostgreSQL 18（镜像 `pgvector/pgvector:pg18`），SQLAlchemy 2.0（asyncpg），Alembic 管迁移；pgvector 镜像预留、功能暂不启用（见 #18）。
**理由**：直接上 PG 免去日后迁移；既然用 PG 就不单独引 Chroma/Qdrant。18 与镜像细节见 #18。

### #2 · LLM 底座
**结论**：国内 OpenAI 兼容端点（智谱/通义/DeepSeek 等），通过 OpenAI SDK 标准变量 `OPENAI_API_KEY`/`OPENAI_BASE_URL` 配置切换（早期写的 `LLM_*` 命名已由 #21 取代）。
**理由**：网络稳定、成本低，兼容 OpenAI SDK。

### #3 · 3D 素材策略
**结论**：纯几何体程序化拼装 low-poly（零美术依赖），关键物件（冷链车/礼盒）后期可换 GLB。
**理由**：出效快，答辩够了。

### #4 · 鉴权方案
**结论**：简单 JWT，双角色（运营方/合作社）；溯源 H5 的 `/api/trace/{code}` 保持公开。
**理由**：约一天工作量，答辩讲"系统完整性"有支撑。

### #5 · 模拟引擎模式
**结论**：可重放固定剧本（参数化随机生成世界 + 可选固定 seed），答辩前跑排练剧本。
**理由**：演示可控、可复现，讲稿与画面不会错位。

### #6 · Agent 编排方式
**结论**：手写编排（openai SDK + 集中 Prompt 管理），不引 LangChain/LlamaIndex。
**理由**：5 个 Agent 工作流清晰可控，答辩讲得清；避免框架黑盒。

### #7 · 任务队列
**结论**：asyncio 后台任务起步，不引 Celery/Redis。
**理由**：演示型项目体量不需要；后期真有耗时任务再加。

### #8 · 状态管理库
**结论**：TanStack Query（REST 缓存与失效）+ Zustand（沙盘实时态与选中对象）双库共存。
**理由**：REST 资源就几类（任务/产出物/基准/溯源），TQ 白送缓存、重验证与加载态；沙盘高频 WS 增量流本就绕开请求缓存，Zustand 正合适。多一个依赖换掉的全是手工活。

### #9 · 溯源 H5 深度
**结论**：MVP 做图文时间线版；"与 IP 角色实时对话"进 M7 冲刺池（缓存对话树优先、实时兜底），不是 MVP 阻塞项。
**理由**：由 #16 高光选择（Agent 内容 + 3D 流动）推出——溯源页职责是闭环收口，不是答辩高光。

### #10 · MVP 中 Agent 覆盖范围
**结论**：MVP = Agent 1（故事）+ Agent 3（文案）+ 溯源页（时间线版）；Agent 2（画图）进冲刺、Agent 5（调度）进展示位。已由 #16 整体定稿。
**理由**：见 #16。

### #11 · 演示数据真实性策略
**结论**：预生成入库为主——答辩前把剧本数据与 Agent 产出全部生成落库，现场演示全命中数据库；保留一个"现场实时生成"演示位作加分项（如评委出题现场写故事）。
**理由**：演示型项目最大风险是现场网络/端点波动，预生成保证断网也能走完整条闭环；实时位仅在网络正常时启用。已写入 02-agents.md §7。

### #13 · 图像生成 API 选型
**结论**：采用 SiliconFlow（硅基流动）OpenAI 兼容文生图网关，Agent 2 走 `https://api.siliconflow.cn/v1/images/generations`（Bearer API Key）；与 #2 的文字端点同构，复用同一套 OpenAI 兼容封装。候选模型 `Kwai-Kolors/Kolors`、`Qwen/Qwen-Image`，Agent 2 启动前实测中文字形与画风后 pin 具体型号。
**附加实现要求**：
1. 返回的图片 URL 仅 1 小时有效 → 生成后必须**下载转存本地**，`agent_artifact` 只存本地路径；
2. 请求头 `X-Enable-Watermark: 0`，**不保留**平台默认「AI 生成」水印；
3. 生成时固定 `seed`，保证可复现（契合 #5 / #11）。
**理由**：一次接入多家生图模型，切换 = 换 `model` 字符串，"选供应商"降为"选模型"，选型风险最低；与既有 LLM 封装同构、胶水代码最少。定价与限流平台文档未列明，注册后在后台确认（已记入 05 未验证假设）。
**文档落点**：实现细节集中在 [02-agents.md](02-agents.md) §2.1（各 Agent 设计当前篇幅不长，暂不拆单一 Agent 文档）。

### #15 · 溯源数据源设计
**结论**：`trace_code` 只锚 `pallet_id`（`shipment_id` 字段删除）；时间线来自 `trace_event` 流水表（append-only，模拟引擎在每个关键节点写入一行）；`pallet` 增加现势字段（current_site_id / current_vehicle_id）供沙盘读取。确立全库统一模式：**现势状态存实体表（沙盘读），历史过程存事件表（溯源页读）**。温度曲线按在途时间段从 `telemetry` 反查。
**理由**：溯源故事的前半段（采摘/包装/入库）没有运单覆盖，纯反查讲不完整；02 文档 4.2 已约定"数据全部来自模拟引擎已落库的历史"，流水表是该承诺的具体落地；单表查询、预生成（#11）、可重放剧本（#5）三者全都受益。

### #16 · MVP 重新切分
**结论**：MVP 按核心叙事闭环重新推导，新验收动线 = **沙盘可看可点 → Agent 1/3 产出 → 润色可改 → 扫码溯源（时间线版）→ 沙盘页内嵌一张溢价对照图**。里程碑重排为：M1 地基（compose 单 db 服务 + Alembic 首版迁移（含 trace_event）+ JWT）→ M2 世界活了（sim 引擎 + WS）→ M3 看得见（3D 沙盘）→ M4 会说话（Agent 1/3 + 工作台润色）→ M5 扫码闭环（溯源 H5）→ M6 会算账（溢价对照图）→ M7 冲刺与包装。**从旧 MVP 移出**：独立数据看板页（降级为沙盘页一张内嵌图，完整看板进冲刺）；溯源页温度曲线为顺手项（telemetry 表本就供给车辆详情卡，曲线渲染不设门槛、不占关键路径）。
**理由**：以 00 文档核心叙事为唯一验收标准重新推导，替代 AI 生成的旧清单；一个月 + 4 人以上配置下可行；答辩高光确认为 Agent 内容生成 + 3D 沙盘流动，资源向 sim 剧本节奏与工作台润色倾斜；溯源页因 #15 的流水表设计而变便宜，升入 MVP 收口"扫码可溯源"。

### #17 · 实时链路接口形状
**结论**：① 模拟时钟控制走 REST 端点 `POST /api/sim/control`（action: pause/resume/speed/reset，限运营方角色），时钟状态变化经既有 `tick.info` 事件广播。② 快照主从定为 **REST 快照为主**：`GET /api/world/snapshot` 读现势全量（3D 初始化、断线重连、深链恢复的唯一入口），WS 只发增量事件（不发快照消息）。
**理由**：控制入口用 REST 则鉴权、防误触、日志全走现成机制；快照走 REST 与 #15 的"现势存实体表（REST 读）/ 历史存事件表（WS 流）"同构，两种传输通道各管一类数据零重叠；WS 层不锁快照逻辑，可 curl 调试，重连 = 重新 GET。

### #18 · 数据库镜像与 pgvector 处置
**结论**：PG 用 18，compose 镜像选 `pgvector/pgvector:pg18`（官方 postgres 镜像 + pgvector 扩展的构建版；纯 `postgres:18-alpine` 不内置扩展，满足不了预留诉求；有 alpine 变体则优先选变体，版本号在 M1 写 compose 时 pin 定）。pgvector 按"镜像预留、功能不启用"处置：MVP 不建知识库表、不写检索逻辑，架构图标注预留；冲刺期若给 Agent 1 上知识库检索，再补 knowledge_chunk 表。
**理由**：2026-10 时点 pgvector 已有 PG18 构建，18 还带异步 I/O 等新特性；预留式镜像让"日后启用"零迁移成本，文档降级又避免架构图挂着无处着力的组件。⚠️ 部署注意：PG 官方镜像 18 起数据卷路径为 `/var/lib/postgresql`（不再是 `/var/lib/postgresql/data`），compose 卷按新路径挂。

### #20 · PG 数据卷宿主机落点（项目目录绑定卷）
**结论**：本地开发阶段，PG 数据卷用**项目目录绑定卷**——宿主机侧挂 `./data/postgres/`（加入 .gitignore），容器内侧挂 `/var/lib/postgresql`（PG18 新路径）。将来部署服务器时改为命名卷（docker managed volume），届时仅需改 compose 一处。
**理由**：演示项目"数据跟着项目走"——项目目录可直接查看/清理/整目录迁移，不藏在 Docker volume 池里；`/var/lib/postgresql` 是容器内侧路径（PG18 起不再带 `/data` 后缀），与宿主机落点是两回事，此前 05 文档未区分两层导致误读。
**拍板时间**：2026-10-16

### #22 · 文本模型初定（GLM-5.3-Flash，已被 #23 取代）
**结论**：**已被 #23 取代**（GLM 的思维链实测结论保留备查）。MVP 文本生成固定用 SiliconFlow 的 `zai-org/GLM-5.3-Flash`，变量名 `OPENAI_MODEL`，`Settings.openai_model` 默认值同名；`OPENAI_BASE_URL` 指向 `https://api.siliconflow.cn/v1`。图像模型仍按 #13 单独选型、单独变量（Agent 2 启动前补），不与文本模型共用。
**实现注意**：该模型默认输出 `reasoning_content`（思维链），正文在 `content`，思维链长度波动大（一句话也可能烧掉 500–1000 tokens）；`max_tokens` 必须覆盖"思维链 + 正文"（短演示 ≥1200，故事类建议 ≥2000），否则 `finish_reason=length` 且正文为空。`enable_thinking=false`、`thinking:{"type":"disabled"}`、`reasoning_effort:"none"` 三种关思考写法实测均被静默忽略（HTTP 200，思维链照常）。
**流式**：`stream:true` 可用（SSE `data:` 行 + `[DONE]` 结尾）；先流 `reasoning_content` 再流 `content`，实测首 token 约 1 秒、正文首字 2.6–7.7 秒；带 `stream_options.include_usage` 时末尾会追加一个 `choices: []` 的 usage 块，解析必须防空 choices。M4 的 `agents/llm.py` 应丢弃思维链、只把 `content` 推给前端，并对"实时生成"演示位做超时兜底。
**验证方法**：`GET /v1/models` 200 且列表含该 id；`POST /v1/chat/completions` 200 返回中文正文；`stream:true` 实测收到 content 增量（2026-10-20 已实测）。
**理由**：与 #13 同网关同一把 key，一套 OpenAI 兼容封装同时覆盖文本与图像；换模型只改 `.env` 一行（#2/#21）。
**拍板时间**：2026-10-20

### #23 · 文本模型改定（DeepSeek-V3.1-Terminus）
**结论**：MVP 文本生成改用 SiliconFlow 的 `deepseek-ai/DeepSeek-V3.1-Terminus`，替换 #22 的 GLM-5.3-Flash；变量名与默认值不变（`OPENAI_MODEL` / `Settings.openai_model`）。图像模型仍按 #13 单独选型、单独变量。
**实现注意**：该模型不输出思维链，正文直出；流式实测首字约 0.7 秒、短问答 1 秒内完成，100 字故事约 9 秒（143 completion tokens）。`stream_options.include_usage` 时末尾仍有 `choices: []` 的 usage 块，解析需防空 choices；正文可能带 Markdown 记号（如 `**`），工作台渲染需处理。无需再尝试关闭思考。
**验证方法**：`GET /v1/models` 200 且含该 id；`POST /v1/chat/completions` 200 返回中文故事；`stream:true` 实测首字 0.68 秒（2026-10-20 已实测）。
**理由**：日常生成更快、无思维链，适合答辩现场"实时生成"演示位；同一 SiliconFlow key 与封装，换模型只改 `.env`（#21/#22 的接口结论不变）。
**拍板时间**：2026-10-20
