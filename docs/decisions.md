> 格式：`#序号 · 标题 · 状态`，已定条目附结论与理由，待定条目附当前倾向与需要谁拍板。

## ✅ 已定

### #1 · 数据库选型
**结论**：PostgreSQL 16+，SQLAlchemy 2.0（asyncpg），Alembic 管迁移，pgvector 做知识库检索。
**理由**：直接上 PG 免去日后迁移；既然用 PG 就不单独引 Chroma/Qdrant。

### #2 · LLM 底座
**结论**：国内 OpenAI 兼容端点（智谱/通义/DeepSeek 等），通过 `LLM_BASE_URL`/`LLM_API_KEY`/`LLM_MODEL` 配置切换。
**理由**：网络稳定、成本低，兼容 OpenAI SDK。

### #3 · 3D 素材策略
**结论**：纯几何体程序化拼装 low-poly（零美术依赖），关键物件（冷链车/礼盒）后期可换 GLB。
**理由**：出效快，答辩够了。

### #4 · 鉴权方案
**结论**：简单 JWT，双角色（运营方/合作社）；溯源 H5 的 `/api/trace/{code}` 保持公开。
**理由**：约一天工作量，答辩讲"系统完整性"有支撑。

### #5 · 模拟引擎模式
**结论**：可重放固定剧本（参数化随机生成世界 + 可选固定 seed），答辩前跑排练剧本。
**理由**：演示可控、可复现，讲稿与画面不会错位。

### #6 · Agent 编排方式
**结论**：手写编排（openai SDK + 集中 Prompt 管理），不引 LangChain/LlamaIndex。
**理由**：5 个 Agent 工作流清晰可控，答辩讲得清；避免框架黑盒。

### #7 · 任务队列
**结论**：asyncio 后台任务起步，不引 Celery/Redis。
**理由**：演示型项目体量不需要；后期真有耗时任务再加。

## ❓ 待定

### #8 · 状态管理库
**倾向**：TanStack Query（REST 缓存）+ Zustand（沙盘实时状态）。
**争议点**：是否接受多一个依赖；纯 Zustand 也可凑合。影响小，可最后定。

### #9 · 溯源 H5 深度
**倾向**：MVP 先做图文时间线版，冲刺阶段再评估"与 IP 角色实时对话"（需缓存对话树 + 实时兜底，防现场网络翻车）。
**需要**：确认答辩动线中溯源页占的分量。

### #10 · MVP 中 Agent 覆盖范围
**倾向**：MVP 只做 Agent 1（故事）+ Agent 3（文案）；Agent 2（画图）/4（溯源）/5（调度）进冲刺或展示位。
**需要**：确认切法是否接受。

### #11 · 演示数据真实性策略
**倾向**：答辩所需数据预生成入库，现场演示全命中数据库；保留一个"实时生成"演示位作加分项。
**需要**：确认后写入 02-agents.md 的 LLM 接入规范。

### #12 · Agent 工作台的页面归属
**倾向**：独立页面（信息架构更清晰）。
**争议点**：若答辩动线希望一动线讲完，可把润色交互折叠进沙盘页侧栏（动线更连贯）。取决于答辩讲稿怎么排。

### #13 · 图像生成 API 选型
**倾向**：暂无（Agent 2 启动前必须定）。
**候选**：通义万相 / 智谱 CogView / 其他国内端点。

### #14 · 答辩演示剧本内容
**倾向**：需要先写答辩讲解词（分镜），再让模拟剧本与讲解词逐条对齐。
**需要**：确定比赛时间节点后倒排里程碑（见 04-roadmap.md）。
